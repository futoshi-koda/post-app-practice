# PR 読み取りレビュー（報告のみ）

PR 番号（`$ARGUMENTS`。例: `2`）の差分を、決まった順で読み、判定つきの表で報告する。**コードは直さない。** 見つけたことは報告だけにする。

## 0. 準備

- `gh pr view <N> --json title,body,files,baseRefName,headRefName,mergeCommit` で、変更ファイル一覧・PR 本文・マージコミットを得る。
- `gh pr diff <N>` をスクラッチパッドのファイルに保存し、**最後まで全部読む**（出力が大きいと省略されるので、`Read` で範囲を分けて読む）。
- 削除行を調べるために、マージ済みなら `git merge-base <マージコミット>^1 <マージコミット>^2` を基点に `git diff <基点> <マージコミット> -- <ファイル>` を使う。
- ユーザーが「読む順」「見る観点」「触っていないはずのファイル」を指定したら、それに従う。指定がなければ下の 1〜3 を使う。

## 1. 設計書との突き合わせ

設計書は、PR に含まれる `docs/*.md`、または Issue に書かれたもの。

- 差分にあるのに設計書に書かれていないもの（ファイル・クラス・設定・共通化・見た目の変更）を挙げる。
- **依存ファイル**（`composer.json` / `composer.lock` / `package.json`）が差分にあるかを、`git diff --stat` で必ず確かめる。なければ「差分に含まれない」を OK として書く。
- 設計書にあるのに、コードにないものを探す（画面・ルート・テーブル・メッセージ・ポリシー）。
- 設計書の「テスト観点」と、実際のテストを突き合わせる（観点があるのにテストがないものを挙げる）。
設計書が無い機能のときは、そのイシューに書いた受け入れ条件を突き合わせ先にする。


## 2. 触っていないはずの場所

設計書の「変えないもの」と、ユーザー指定のファイルを見る。**消えた行から先に**見る。

- 各ファイルについて、削除行数・追加行数と、削除行の中身を出す。
- 「移動しただけ」に見える削除（CSS・配列・検証ブロックなど）は、削除側と追加側を `diff` で機械的に照合し、同じ内容か、差が何行かを確かめる。目で見ただけで「同じ」と書かない。
- 差分にまったく含まれないファイルは「差分に含まれない」で OK とする。

## 3. 中身

次の観点を 1 つずつ見る。

- **N+1**: コントローラの eager load と、ビュー内のリレーション参照・`@can`。
- **認可の置き場所**: `authorize()` をどこで呼ぶか、既存コントローラと揃っているか。ポリシーは自動検出（`AuthServiceProvider::$policies` に登録しない）。認可が要らない操作は「設計書どおりか」を確かめる。
- **マスアサインメント**: `$fillable` と、`create` / `update` に渡る配列に何が入るか（`validated` 以外が混ざらないか）。
- **XSS**: `{!! !!}` の有無、`style` 属性などに入る値の出どころ。
- **CSRF**: フォームの `@csrf` / `@method`。テストでは CSRF 検証が無効なので、実際の動きは「判定不可」になる。
- **入力チェック**: ルール・日本語メッセージ（`ValidatesContent` と `$request->validate($rules, $messages)` の書き方）・型の想定外入力（配列など）。
- **書き方の揃い**: 既存コードとの揃い、`.claude/rules/testing.md` の決まり。ただし、決まりが **PR より後に作られた**場合は「対象外」とし、その旨を書く。

## 4. 報告の形

1 行 1 観点の表にする。列は **観点 / 判定 / ファイル名:行番号 / 気づいたこと**。

- 判定は 3 値: **要確認** / **OK** / **対象外**。
- **判定できないときは、「判定不可」とし、何が足りないか**（画面を開いていない・テストを実行していない・CSRF の実動作が見られない、など）を書く。
- 行番号は、差分のハンクの開始行から数えた **PR 時点のファイルの行**。現在の main とずれるなら、その旨を書く。
- 見つけた問題を断定しない。実行していないことは「〜のはず（実行していません）」と書く。
- PR 本文のテスト結果は、PR 本文の記述として扱う。自分で実行していなければ「実行していない」と明記する。
- PR より後に入った変更との相互作用（例: ルートの定義順）は、現在の main を見て、短く 1 行で添える。

表のあとに、**人が自分の目で読むべき場所を 3 つまで**挙げる。それぞれ、なぜそこか（既存の動きに触れている・実動作が未確認など）を一言添える。

## やらないこと

- コードの修正・コミット・PR へのコメント投稿。
- 差分を読み切らずに判定すること。
- 設計書にない変更を、それだけで「悪い」と断定すること（「要確認」として挙げ、判断は人に渡す）。
